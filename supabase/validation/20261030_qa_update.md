# QA schema update — 2026-10-30

## Published schema scope

The installer bootstrap now contains 183 migrations: the unchanged 145-file
2026-10-27 captured baseline followed by 38 canonical forward migrations through
`20261030220000_procurement_quotation_detail.sql`.

The additions cover procurement policies, suppliers, requests, tenders,
publication and approval history, quotation capture, credentials/evidence,
replenishment, personal/business participation, drafts, free-text quotations,
quotation envelopes, receipt activity and buyer quotation details. They also
include POS cancellation and cloud document/requirement-session persistence.

`bootstrap/manifest.json` remains the installer's complete file/hash contract.
Its original capture metadata and runtime evidence still describe only the
baseline. Formatting was compacted to keep the manifest below 500 lines without
changing baseline entries. `bootstrap/upgrades-20261030.json` separately records
the added files, hashes, provenance and validation limitations.

Every upgrade is byte-identical to its canonical `supabase/migrations/` copy.
Frontend copies come from the sibling `market-fit` checkout; the two cloud copies
already existed in this repository and were preserved. Older frontend migrations
were not bulk-copied or replayed: their objects are captured in the baseline,
and the historical directory is not a complete fresh-install path.

No old migration SQL or baseline SQL was edited. Previously untracked migration
and targeted-validation artifacts are included; their remote-application evidence
is historical and was not reverified against a remote project in this task.

## Static validation and safety

```bash
python3 scripts/validate-bootstrap.py
PYTHONDONTWRITEBYTECODE=1 python3 scripts/test_validate_bootstrap.py
```

Static validation checks exact coverage, unique versions/names, hashes, date
prefixes, files below 500 lines, canonical equality and existing baseline guards.
Six offline regression tests cover valid artifacts, duplicate manifest entries,
canonical drift, unlisted SQL, function-body versus top-level insert handling,
and unreviewed inserts even when both manifests and canonical hashes agree.

Only three reviewed upgrades may contain top-level INSERT statements:

- Credentials: creates the private `procurement-credentials` Storage bucket.
- Replenishment queue: derives pending work from local inventory rules.
- Lifecycle repair: reconstructs historical tender policy bindings from the
  target's own saved publication/request audit history, failing closed when
  historical provenance is unavailable.

These are migration effects, not exported customer fixtures. Baseline no-row,
Auth-trigger, Storage-policy and local-only workflow-webhook safeguards remain.
Installer schema preflight is checked without invoking create, package or deploy;
it stops at the intentionally absent private installer configuration.

## QA operator handoff and remaining gates

1. Use the published schema revision with compatible reviewed frontend, API and
   workflow revisions. QA packaging requires those source checkouts to be clean.
2. For a **new** isolated QA Supabase, explicitly select this repository's
   `bootstrap/` directory through the existing QA installer. Its manifest covers
   all 183 files, which are packaged into the temporary Supabase migration path.
   A fresh QA ID, reviewed-schema acknowledgement and separate infrastructure
   cost approval remain required. This update does not create paid resources.
3. For an **existing** QA database, do not apply the captured baseline. Inspect
   its actual objects and migration history, reconcile captured versus historical
   versions, and apply only compatible missing forward migrations with explicit
   approval of the exact target. A Git push alone does not mutate the database.
4. Validate the full ordered bootstrap plus upgrades in platform-complete
   Supabase, including actual Auth, Storage, extensions, grants and RLS. This
   machine has no Docker CLI; a full updated Supabase replay was not performed.
5. Provision deterministic disposable QA users, roles, sites and synthetic data
   using the frontend's `docs/QA_PROVISIONING.md`. The current fixture battery
   is not a fixture set for every new procurement/cloud workflow; add those
   explicitly. Schema availability does not imply module-wide E2E coverage.
6. Run the selected, authorized browser suites and both allowed/denied role and
   tenant journeys. Configure local workflow receivers, Storage test objects and
   any required external integration test environments separately. Paid Stripe,
   provider lifecycle and full checkout flows remain separate verification gates.

No remote migrations, deployment, production build, QA database reset,
provisioning, paid infrastructure creation or browser tests were performed.
